# Спецификация требований к проекту "Online Bookstore"

## 1. Бизнес-требования
* **Назначение системы:** Веб-приложение для автоматизации онлайн-продажи книг, управления каталогом литературы, складскими запасами, заказами клиентов и сбора аналитики продаж.
* **Какую проблему она решает:** Упрощает процесс поиска и заказа печатных изданий для пользователей, а для владельцев магазина автоматизирует рутинные операции по учету книг, обработке заказов, расчету скидок по промокодам и ведению финансовой статистики.
* **Цели, которые должны быть достигнуты:**
  1. Обеспечить круглосуточный доступ пользователей к каталогу книг с возможностью быстрого поиска и фильтрации.
  2. Автоматизировать процесс резервирования книг на складе и управление статусами заказов (от создания до выдачи/продажи).
  3. Предоставить администраторам и сотрудникам инструменты аналитики (графики продаж, расчет средних чеков, популярные жанры) и импорта книг через внешние API.

## 2. Пользовательские требования (Use Cases)
*Ниже описаны ключевые сценарии взаимодействия пользователей с системой:*

1. **UC-1: Регистрация и аутентификация клиента**
   * *Актёр:* Новый или зарегистрированный пользователь.
   * *Описание:* Пользователь заполняет форму регистрации (указывает логин, почту, телефон по маске РБ, дату рождения, город и адрес). Система проверяет возраст (18+) и уникальность данных, после чего создает профиль (`Client`) и выполняет вход в систему.

2. **UC-2: Поиск и фильтрация литературы**
   * *Актёр:* Любой пользователь (авторизованный или анонимный).
   * *Описание:* Пользователь вводит ключевые слова в поисковую строку (поиск по названию книги или автору) либо выбирает параметры сортировки (по цене, по названию), после чего система выдает отфильтрованный и постранично разбитый список книг.

3. **UC-3: Управление корзиной и резервом книг**
   * *Актёр:* Авторизованный клиент.
   * *Описание:* Клиент добавляет доступную книгу из каталога в свой заказ. При этом конкретный экземпляр книги (`BookInstance`) переходит из статуса "доступна" (`a`) в статус "зарезервирована" (`r`). Клиент может увеличивать или уменьшать количество экземпляров.

4. **UC-4: Оформление и подтверждение заказа**
   * *Актёр:* Авторизованный клиент.
   * *Описание:* Перейдя к оформлению заказа, клиент выбирает тип доставки (курьер с указанием адреса или самовывоз с выбором пункта выдачи `PickupPoint`), при необходимости вводит промокод для скидки и подтверждает заказ, переводя его в статус «в обработке» (`p`).

5. **UC-5: Обработка заказов и управление складом (Сотрудник)**
   * *Актёр:* Сотрудник или администратор магазина.
   * *Описание:* Сотрудник заходит в закрытую панель управления, просматривает список активных заказов, меняет их статусы на «выполнен» (`d`) при выдаче клиенту (что переводит книги в статус «продано» — `s`), а также управляет остатками и импортирует новые книги через внешнее API.

## 3. Функциональные требования
1. Система должна позволять пользователям регистрироваться с указанием логина, email и пароля.
2. Система должна проверять возраст пользователя при регистрации (клиент должен быть старше 18 лет).
3. Система должна валидировать номер телефона клиента по строгому формату Республики Беларусь (`+375(XX)XXX-XX-XX`).
4. Система должна предоставлять каталог книг с постраничной пагинацией (по 12 товаров на страницу).
5. Система должна осуществлять поиск книг по подстроке в названии книги или в именах авторов.
6. Система должна позволять сортировать каталог книг по названию (алфавиту) и по цене (возрастание/убывание).
7. Система должна разрешать авторизованным клиентам добавлять книги в текущий активный заказ (создавать резерв экземпляра `BookInstance`).
8. Если у книги отсутствуют доступные экземпляры (`status='a'`), система должна автоматически предлагать клиенту добавиться в лист ожидания (`Waitlist`).
9. Система должна позволять клиенту управлять количеством экземпляров книг в заказе (увеличивать или уменьшать количество).
10. Система должна поддерживать применение активных промокодов (`PromoCode`) для расчета процентной скидки от общей суммы заказа.
11. Система должна позволять клиенту отменять свой заказ, если он находится в статусе «Новый» (`n`), при этом автоматически возвращая зарезервированные экземпляры книг в свободный статус (`a`).
12. Система должна предоставлять форму подтверждения заказа с выбором метода доставки (курьер или самовывоз из конкретного пункта выдачи `PickupPoint`).
13. Система должна ограничивать доступ к панели управления заказами, статистике и импорту книг только для пользователей с правами сотрудника или администратора (`staff_or_employee_required`).
14. Сотрудник должен иметь возможность переводить заказ в статус «Выполнен» (`d`), что автоматически изменяет статус связанных экземпляров книг на «Продано» (`s`).
15. Система должна автоматически назначать появившуюся на складе книгу первому в очереди клиенту из листа ожидания (`Waitlist`) при добавлении новых экземпляров через панель управления.
16. Администратор должен иметь возможность импортировать книги из внешнего источника (Google Books API) с автоматическим скачиванием обложек и созданием начальных складских единиц.
17. Система должна генерировать аналитические отчеты и графики продаж (с использованием Matplotlib) на странице статистики для сотрудников.
18. Система должна логировать важные действия пользователей (регистрация, ошибки форм, отмена заказов, действия администраторов) в консоль и файл `app_debug.log`.

## 4. Нефункциональные требования
1. **Безопасность:** Пароли пользователей не должны храниться в открытом виде; система должна использовать стандартные криптографические алгоритмы хеширования паролей Django.
2. **Производительность:** Время отклика страниц каталога и поиска при стандартной нагрузке не должно превышать 2 секунд.
3. **Надежность и обработка ошибок:** В случае сбоев при запросах к внешним API (например, погода или Google Books) приложение не должно «падать» (выдавать ошибку 500), а должно корректно перехватывать исключения (`try-except`).
4. **Масштабируемость данных:** Архитектура базы данных на базе Django ORM должна обеспечивать возможность бесшовного переключения со встроенной SQLite на промышленную СУБД (PostgreSQL) без изменения программного кода.
5. **Удобство сопровождения (Maintainability):** Код проекта должен быть структурирован по принципу разделения ответственности на приложения (`store` и `pages`), содержать документированные модели и соответствовать стандартам PEP 8.
6. **Адаптивность интерфейса:** Пользовательский интерфейс должен корректно отображаться на экранах различных устройств (ПК, планшеты, смартфоны) благодаря использованию адаптивных HTML-шаблонов.
