# Отчет о проведении базовых проверок безопасности (Security Testing Report)

В рамках выполнения Задания 4 (пункт 3) был проведен аудит безопасности веб-приложения «Online Bookstore» на предмет типовых уязвимостей (OWASP Top 10).

---

## 1. Проверка доступа в авторизованную зону без авторизации
- **Цель проверки:** Убедиться, что неавторизованные пользователи не имеют доступа к приватным страницам и панели управления.
- **Тестируемые маршруты:**
  - `/my-orders/` (Личный кабинет клиента)
  - `/order-management/` (Панель управления заказами)
  - `/import_books/` (Импорт книг через API)
  - `/stats/` (Аналитика и финансовая статистика)
- **Методика:** Отправка прямых GET-запросов к указанным URL-адресам без передачи сессионных cookie (`sessionid`).
- **Фактический результат:** Запросы перехватываются декораторами `@login_required` и `@staff_or_employee_required`. Сервер возвращает код ответа `302 Found` с редиректом на `/login/` либо на главную страницу каталога.
- **Статус проверки:** **PASS (Уязвимость отсутствует)**.

---

## 2. Проверка защиты от подмены идентификатора (IDOR)
- **Цель проверки:** Проверить невозможность модификации или просмотра чужих данных путем манипуляции ID в параметрах запроса.
- **Тестируемый сценарий:**
  - Клиент А имеет заказ с экземпляром книги `id = 1`.
  - Клиент Б авторизуется в системе и отправляет запрос на изменение количества книги в чужом заказе:
    `GET /my-order/update/1/increase/`
- **Анализ реализации:** В контроллере `store.views.update_my_order` выполняется явная валидация владельца ресурса:
  ```python
  if order.client.user != request.user:
      return redirect('my_orders')
  ```
- **Фактический результат:** Запрос отклоняется системой, чужие данные не изменяются, происходит принудительный возврат пользователя (злоумышленника) в его собственный список заказов.
- **Статус проверки:** PASS (Уязвимость отсутствует).

---

## 3. Анализ сообщений об ошибках и раскрытия чувствительных данных (Information Disclosure)
- **Цель проверки:** Убедиться, что при возникновении программных исключений и кодов 404/500 сервер не раскрывает внутреннее устройство системы (трассировку стека, структуру БД, абсолютные пути на сервере, выполняемые SQL-запросы).
- **Тестируемый сценарий:** Обращение к заведомо несуществующему ресурсу `/book/999999/` и передача некорректных параметров.
- **Фактический результат:** В текущей конфигурации сборки на хостинге (Render.com) включен режим отладки `DEBUG = True`, из-за чего отображается системная страница Django с указанием используемых шаблонов URL, локальных переменных и путей к файлам.
- **Рекомендация по устранению:** Для продуктивной среды (Production) необходимо установить переменную окружения `DEBUG = False` (через **.env** файл на хостинге), чтобы Django автоматически скрыл системные данные и отдавал безопасные стандартные шаблоны **404.html** и **500.html**.
- **Статус проверки:** FINDING (Замечание зафиксировано в журнале дефектов / ISSUES.md).

## 4. Проверка системы аудита и логирования
- **Цель проверки:** Подтвердить фиксацию критических событий системы, системных сбоев и попыток несанкционированного доступа.
- **Анализ реализации:** В файле конфигурации `core/settings.py` детально сконфигурирован модуль `LOGGING`, отслеживающий события приложений `store` и `pages` с записью в файл `app_debug.log`.
- **Фактический результат:**
Фиксируются попытки несанкционированного доступа к панели управления (уровень WARNING):
`Unauthorized access attempt to {view_func} by user {username}`.
Подробно фиксируются ключевые бизнес-операции (уровень INFO): создание новых пользователей, оформление заказов, резерв книг на складе, применение промокодов.
Фиксируются сбои и недоступность внешних `API`, таких как `OpenWeatherMap` (уровень ERROR).
- **Статус проверки:** PASS (Требование выполнено в полном объеме).
